# 异动提醒表比赛排序混乱问题分析

## 现象

浏览器 HTML 报告里的“变盘异动提醒”卡片区域、下方全量比赛表格的“变盘异动”列等，排序结果看起来不稳定：

- 同样等级（重点关注 / 关注 / 稳定）的比赛，场次编号经常不是 1 → 14 升序，而是跳着出现。
- 有时同一等级里，编号靠前的比赛反而排在后面。
- 多次运行同一期数据，排序结果可能不一致（取决于并发抓取结果到达顺序）。

## 根因

排序逻辑在 `football_analysis/browser_report.py`（以及 `report.py` 里的 markdown 版本，`query_report.py` 的查询页也有类似模式）：

```python
_MOVEMENT_ORDER = {"重点关注": 3, "关注": 2, "稳定": 1, "无数据": 0}

items.sort(
    key=lambda item: (
        -_MOVEMENT_ORDER.get(_movement_level(item), 0),
        int(item.get("match_no") or 0),
    ),
)
```

表面上排序键是 `( -等级权重, 场次编号 )`，逻辑是对的。但问题出在 **`match_no` 字段本身不稳定**：

1. **`match_no` 来源是赛程抓取，不是分析排序的权威源。** 在 `pipeline.py` 里，`fixture_id` 和 `match_no` 都是抓取出来的字符串。如果某场比赛抓取的 `match_no` 缺失或为空，代码用 `int(item.get("match_no") or 0)` 兜底成 `0`，导致这些比赛全部排在最前面，且彼此之间再无排序依据。

2. **Python 的 `sort` 是稳定排序，但输入顺序依赖并发抓取的完成顺序。** `_attach_odds_movement` 用 `ThreadPoolExecutor` 并发抓 `fetch_nowscore_movement`，`future.result()` 的返回顺序不固定。虽然最后 `analyses` 列表本身在 `pipeline.py` 里是按 `fixture_id` 排序后组装的（见 `urls = {team_id: ... for team_id in sorted(team_ids)}`），但 `fixture_id` ≠ `match_no`。如果 `fixture_id` 与 `match_no` 的映射不是一一对应的（比如一期里某场 `fixture_id` 重复、或 `match_no` 有重复值），稳定排序的同键元素就会保留“不确定的原始顺序”，表现为跳号。

3. **`_movement_level` 的兜底值 `"无数据"` 在 `_MOVEMENT_ORDER` 里权重为 0。** 如果某场比赛的 `odds_movement` 字典缺失或 `level` 字段缺失，会被当成“无数据”排到最后。但如果 `reasons` 非空而 `level` 缺失（数据组装 bug），排序键又变成 `(0, match_no)`，和真正“无数据”的比赛混在一起，进一步加剧视觉混乱。

4. **`query_report.py`（查询页）的排序是另一套逻辑。** 它走的是 `store.py` 的 `query_movements`，SQL 里是：

   ```sql
   ORDER BY captured_at DESC, issue DESC, ...
   ```

   这里没有按 `match_no` 排，而是按入库时间 `captured_at` 倒序。如果同一期多次入库（比如手动重跑），`captured_at` 不同，顺序就会和报告页的 `match_no` 升序完全不同，用户会觉得“排序混乱”。

## 建议

按优先级：

1. **统一排序键，保证全链路一致。** 所有展示异动比赛的界面（HTML 报告、查询页、markdown 报告）都用同一个排序函数：

   ```python
   def _movement_sort_key(item: dict) -> tuple:
       movement = item.get("odds_movement") or {}
       level_weight = _MOVEMENT_ORDER.get(movement.get("level"), 0)
       match_no = int(item.get("match_no") or 0)
       # 兜底：缺失 match_no 的比赛，用 team 名做第二排序键，避免全部堆在 0
       team_key = (item.get("home_team", ""), item.get("away_team", ""))
       return (-level_weight, match_no, team_key)
   ```

   关键改动：把 `team_key` 加进排序键，让“同等级 + 同/缺失 match_no”的比赛也有确定顺序。

2. **把 `match_no` 缺失视为数据问题，而不是静默兜底成 0。** 在 `pipeline.py` 组装 `analyses` 时，如果 `match_no` 缺失，记一条 warning；在排序键里，缺失时给一个很大的哨兵值（比如 `999`），让这些比赛排到最后，而不是最前面。

3. **查询页（`query_report.py` + `store.py`）的 SQL 排序对齐报告页。** 在 `query_movements` 的 SQL 里加上 `home_team, away_team` 作为 `captured_at` 之后的兜底排序键，或者干脆改用 `match_no` 字段（如果表里有的话，需要确认 schema）。目前 `match_movements` 表没有存 `match_no`，只有 `home_team` / `away_team`，建议加一列 `match_no` 并在 `save_issue_movements` 里写入，这样查询页也能按场次编号排。

4. **在 `store.py` 的 `save_issue_movements` 里，把 `movement` 的原始 JSON 存到 `movement_json` 列时，同时把 `match_no` 也存进去。** 这样查询页可以恢复“按场次编号”排序，和报告页一致。

5. **加一个回归测试。** 在 `tests/test_odds_movement.py` 或新增 `tests/test_sorting.py` 里，构造 14 场 mock 数据（其中 2 场 `match_no` 缺失、3 场同等级），断言排序结果在重复运行下完全一致，且 `match_no` 缺失的比赛不排在最前面。

## 最小改动方案

如果不想动 schema，最小改动是：

- 在 `browser_report.py` / `report.py` / `query_report.py` 里，把排序键统一成 `(-level_weight, match_no or 999, home_team, away_team)`。
- 查询页的 SQL 在 `ORDER BY` 里加上 `home_team, away_team`（`store.py` 的 `query_movements`）。

这样不动数据库 schema，排序就稳定了。`match_no` 缺失的比赛会被推到同等级最后，而不是堆在最前面。
